# Database Architecture

## Decision

The planned system uses PostgreSQL with Prisma ORM. Relational constraints, joins, mature transactional semantics, and consistency across catalog, inventory, identity, and orders motivate PostgreSQL. Prisma provides typed data access and reviewed migrations while preserving the need to understand generated SQL and query behavior.

The API owns a Prisma 7.10.0 configuration, generated-client boundary, sixteen implemented Admin-authentication and Clothing Catalog models, and two reviewed additive migrations. The owner-approved Admin design is recorded in the [S1-T02 schema proposal](../work/sprint-01/s1-t02-schema-proposal.md); the catalog design is recorded in the [S2-T02 schema proposal](../work/sprint-02/s2-t02-schema-proposal.md). S1-T03 and S2-T03 implemented and PostgreSQL-verified those persistence structures against isolated disposable development/test databases. The canonical generation and migration-review process is defined in [Prisma Development and Migration Workflow](../development/prisma.md).

Local development uses the exact official `postgres:18.6-alpine3.24` image through the root Docker Compose configuration. Development and test databases are isolated as `automotive_dev` and `automotive_test`; their lifecycle and guarded reset contract are defined in [Local PostgreSQL Development](../development/local-postgresql.md). This local configuration does not decide production hosting, credentials, backup, or recovery.

## Initial conceptual entities

- Admin identity/access: `AdminUser`, `Role`, `Permission`, plus explicit many-to-many assignments. `SUPER_ADMIN` is a Role, not a boolean shortcut.
- Admin authentication uses separate accepted concepts:
  - `AuthSession` represents one browser/device login and conceptually contains `id`, `adminUserId`, a hash of its random session-bound CSRF token, `createdAt`, `expiresAt`, `revokedAt`, and `lastUsedAt`.
  - `RefreshToken` belongs to an `AuthSession` and represents one credential in its rotating history/family. It conceptually contains `id`, `sessionId`, the SHA-256 token hash, `createdAt`, `expiresAt`, `rotatedAt`, `revokedAt`, and `replacedByTokenId`. The current token also needs bounded AES-256-GCM recovery-envelope metadata (ciphertext, unique nonce, authentication tag, key ID, and expiry) that becomes unusable after the accepted ten-second grace window.
- Clothing catalog: `Product`, `ProductVariant`, `ProductImage`, and self-referencing `Category`. Product owns name, description, Category, lifecycle, and Product Images. `ProductVariant` is the sellable size/color combination and owns globally unique SKU, price, active status, and inventory. Every Product has at least one Variant; a Product without selectable options uses one default unnamed Variant. Product Image uses contiguous Product-unique positions zero through eight, with position zero as the single main image; public eligibility follows Product lifecycle. Storage metadata uses generated keys, with a recoverable staged/compensating lifecycle and durable identification of cleanup still requiring retry. Generic attribute/EAV systems, Variant image ownership, and speculative variant/media abstractions are excluded. Brand is optional future scope rather than a required initial table.
- Stock: exactly one `Inventory` row per `ProductVariant`, created in the same transaction and storing database-constrained non-negative integer `onHandQuantity` plus an optimistic version. Sprint 2 available quantity equals on-hand quantity. Multi-location, reservations, and adjustment history are Deferred.
- Application commerce settings: a singleton persisted `RIAL`/`TOMAN` price-display/input unit defaults to Toman. Required Product Variant prices use positive integer rials divisible by 10 as canonical storage. Changing the setting never rewrites price rows or changes Backend/payment arithmetic.
- Catalog authorization reference data: `catalog.read`, `catalog.manage`, `inventory.update`, `product.media.manage`, and `settings.price.display.unit.update`, each explicitly linked to the existing `SUPER_ADMIN` Role without a wildcard.
- Commerce: `Customer`, `Address`, `Order`, `OrderItem`.

`AdminUser`, `AuthSession`, and `RefreshToken` separation and the fields above are accepted conceptual architecture: refresh credentials rotate while a logical session continues, enabling history, idempotent encrypted grace recovery, replay detection, logout, session revocation, and auditing. The accepted S1-T02 contract uses explicit `AdminUserRole`/`RolePermission` joins, durable HMAC-keyed login and per-session refresh throttle buckets, fixed absolute session expiry, a same-session linear refresh chain, a migration-managed unique partial current-token index, explicit referential actions/CHECK constraints, and terminal security-history retention of 30 days. Per-IP state may remain process-local only while deployment is single-instance.

The detailed Admin field types, nullability, constraints, indexes, lifecycle, cleanup, and initial migration plan are canonical in the [S1-T02 schema proposal](../work/sprint-01/s1-t02-schema-proposal.md). The catalog model, constraints, indexes, triggers, reference data, and migration risk analysis are canonical in the [S2-T02 schema proposal](../work/sprint-02/s2-t02-schema-proposal.md). `schema.prisma` and the two reviewed migrations implement both designs; S1-T03 and S2-T03 verified their database-enforced invariants and coexistence on isolated disposable databases. Catalog runtime repositories/services begin only in later Sprint 2 tasks.

`AdminUser` and `Customer` are independent business identity models unless a future decision changes that boundary. Other entities are discovery inputs, not approved tables. Pricing history, order snapshots, timestamps, and audit fields remain Open or Deferred until their feature/schema planning stage. Product/Variant responsibility, immutable opaque UUID identifiers, required fields, Variant-owned normalized globally unique SKU, default-versus-named Variant exclusivity, and Product-unique normalized size/color combinations are accepted as defined above. Product lifecycle is `DRAFT`, `ACTIVE`, or `ARCHIVED`; Sprint 2 exposes no hard-delete Product contract, only Active Products and their active Variants are public, and zero inventory is represented as unavailability rather than a lifecycle change. Category uses immutable UUID, normalized sibling-unique name, and nullable self-referencing parent; atomic subtree moves enforce cycle and six-level-depth rules, while restrictive deletion permits only empty leaves and never cascades to Products or children. Variant-owned Inventory stores non-negative integer on-hand quantity and an optimistic version; stale absolute updates fail rather than overwrite, while location, reservation, history, and purchase decrement/release behavior are Deferred. Required Variant prices are positive integer rials divisible by 10; a singleton Toman-default display/input setting never rewrites canonical prices, and Backend/payment arithmetic remains rial-based. Multi-category Product membership and final Storefront slug/URL strategy are Deferred.

## Design principles

Model business invariants with database constraints where practical, not application checks alone. Define nullability, uniqueness, foreign keys, indexes, precision, time zones, and delete policies intentionally. Preserve transaction-time facts on orders rather than relying on mutable catalog records. Avoid N+1 access and verify query plans for important paths.

Every migration requires review for data loss, locking, deployment compatibility, rollback/forward-recovery, backfills, and indexes before application. Raw SQL is acceptable only when justified, reviewed, parameterized, and tested. Production data access, backup/restore, retention, privacy, and zero-downtime migration strategy are open operational decisions.

Sprint 2 catalog persistence implements the approved observable invariants in the [Clothing Catalog specification](../features/catalog/specification.md) through the accepted and implemented S2-T02 schema/migration proposal. Runtime contracts remain separately scoped to S2-T04 through S2-T09.
